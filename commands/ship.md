---
description: Review uncommitted changes, branch if needed, commit, and push
---

Ship the current uncommitted changes in this repository. Work through every step
below, then report the result.

## Current state

- Branch: !`git branch --show-current`
- Default branch: !`git symbolic-ref --short refs/remotes/origin/HEAD 2>/dev/null || echo main`
- Status: !`git status --short`
- Diff stat: !`git diff --stat && git diff --cached --stat`
- Recent commit style: !`git log --oneline -15`

## Steps

1. **Review the changes.** Read the full picture: `git status --short`, `git diff`,
   and `git diff --cached`, plus any changed files you need to grasp the intent.
   Identify what the changes actually do and whether they form one coherent unit of
   work. Do not commit secrets or stray artifacts — if you see real secrets,
   gitignored-looking local config, database files, logs, build output, or debug
   leftovers staged or untracked, stop and ask me before doing anything. If the
   changes are unrelated to each other, stop and ask me how to split them.

2. **Decide the branch.**
   - If the current branch is the default branch (`main`/`master`), always create a
     new branch for the changes.
   - Otherwise keep the current branch when the changes fit its scope. Create a new
     branch (off the current HEAD) only when the changes are a distinct, unrelated
     unit of work.
   - Before branching, run `git fetch origin` and note if the remote default branch
     is ahead of local; branch from the current HEAD and mention the gap in the
     report.

3. **Name the branch.** Lowercase kebab-case with a `feat/` or `fix/` prefix, based on
   what the changes do rather than the file names — e.g. `feat/history-format`,
   `fix/stats-drop`. If the current branch already has a suitable name, keep it.

4. **Write the commit message.** Match the style already used in this repository's
   `git log` (see "Recent commit style" above) — casing, prefixes, separators, and
   length. When there is no clear convention, use a terse lowercase
   `<scope>: <imperative summary>` with no trailing period. Add a short body only
   when the summary cannot carry the why. Never mention that the message or branch
   was generated by a tool, and never add co-author trailers.

5. **Commit.** Create the branch if needed (`git switch -c <branch>`), stage only the
   files you reviewed and intended to ship (`git add <paths>`, never a blind
   `git add -A`), then commit. If there is nothing to commit, stop and say so.

6. **Push.** Push to `origin` with upstream set: `git push -u origin <branch>`. If the
   push is rejected because the remote moved, do not force push — report it.

## Report

Finish with a short summary: the branch name (and whether it was new), the commit
hash, the full commit message, and the push result. If you stopped at step 1 or 5,
state exactly why.
